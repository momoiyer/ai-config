# Baseline for suitable new GitHub repositories

Create only configuration justified by the detected repository, preserving existing files. This is a local setup preference, not authorization to change remote settings or buy services.

- Inspect filenames and safe manifests/CI first. Never read `.env` variants, credentials, or local secret configuration. Add project-relevant ignores for secrets, local overrides, build output, caches, and backups. Use a separately named sanitized schema when configuration examples are needed. Verify ignores with `git check-ignore` and tracked filenames with `git ls-files`; ignores do not untrack files or erase history.
- CI: on pull requests and pushes to the actual default branch, run existing verified tests and applicable lint/type/build commands with the existing package manager/lockfile. Do not invent scripts, install unnecessary frameworks, or give a docs-only repository meaningless build jobs. Use supported stable runtimes and official Actions pinned to verified full commit SHAs with version comments. Set minimal `permissions` (normally `contents: read`), timeouts, concurrency cancellation, and disable persisted checkout credentials when unnecessary. Handle fork PRs without secrets; do not run untrusted PR code with `pull_request_target` or privileged runners.
- Dependabot: configure supported detected ecosystems and `github-actions` with weekly updates and a modest PR limit. Group compatible updates by purpose, not every major upgrade together. It is configuration, not an Actions workflow. No package manifest means no invented package ecosystem. Never add auto-merge.
- Dependency review and CodeQL: add only for supported repositories/languages after verifying account/plan eligibility, benefit, permissions and cost. They are conditional additions, not universal checks.
- Recommend GitHub secret scanning/push protection and branch rules requiring the real CI check names when available. These are remote settings: report that they require separate activation and approval, and do not claim YAML enabled them. Scanners miss some secrets/private data. Never add publishing/deployment/release, external notification, broad write permissions, or paid scans as a baseline.
- Lightweight local hooks can help with deterministic safe-path/format checks where compatible with existing tooling. Review their code and lifecycle, make failures actionable, and document bypass/installation limits; hooks alone cannot enforce confidentiality. Never add observation or activity collection.

Validate local commands and workflow structure; report hosted CI as unrun until a real run is observed. Keep the baseline in a small coherent PR. Check current stable releases and eligibility again when applying this guidance.

Primary references: [Git ignores](https://git-scm.com/docs/gitignore), [GitHub secure Actions](https://docs.github.com/en/actions/reference/security/secure-use), [Dependabot setup](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/configure-version-updates), [dependency review](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-review), [security settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-security-and-analysis-settings-for-your-repository).
