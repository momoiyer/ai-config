---
name: feedback-reflection
description: Apply user feedback to reusable working preferences, agent roles, or skills across projects. Use after a meaningful correction or repeated workflow; does not monitor other sessions or collect activity.
---

Use feedback available in the current conversation or explicitly supplied safe evidence. Identify the concrete correction, whether it is supported, and its scope: durable user preference, verified project fact, role expertise, or reusable procedure. Respect an informed reasonable preference. If feedback conflicts with safety, evidence, or a public contract, explain once and recommend a concrete alternative. Confirm uncertain inferences before persisting them.

Find canonical AI Config from the sibling installed `source.json` (the installer writes only a local repository pointer) or an explicitly known checkout. Validate that the directory contains the expected README, global/AGENTS.md, agents/, skills/, and scripts/manage.py; do not scan the home directory, transcripts, other projects, or secret files to find feedback. If the pointer is absent, stale, or inaccessible, report the location problem and a minimal proposed patch; never claim persistent memory was updated.

The coordinating parent owns canonical maintenance; a delegated or read-only agent reports the correction to the parent unless explicitly assigned sole write ownership. Inspect target checkout status, branch, relevant instructions, and only affected safe files. Preserve unfinished work and do not switch another project's checkout away from user work. Use a dedicated task branch when clean and appropriate; otherwise keep the proposed update separate and report any conflict. A correction authorizes narrow reversible local maintenance of this repository, not Git commits/pushes, project data export, tool execution permissions, or permission bypasses.

Choose one canonical home: global/AGENTS.md for cross-project preferences, agents/<role>.toml for distinct role behavior, the existing SKILL.md for a repeatable procedure, or the current project's guide for repository facts. Sanitize to a general rule; never copy conversations, project names, customer/task data, paths, secrets, or local activity into shared instructions. Prefer a small amendment to adding another skill/role. Skills describe procedures; agents describe expertise/ownership; hooks implement deterministic event checks. Suggest a new specialist only for a recurring gap with a bounded responsibility.

Before editing, compare the affected safe source and installed targets against the current committed source. If the affected source already contains unrelated edits, or its installed counterpart has unrelated divergence, leave the correction as a proposed patch and report activation pending; do not bundle or overwrite those edits. Unrelated dirty files elsewhere need not block a disjoint source correction, but do not switch that checkout away from its current work. Apply the smallest supported correction automatically when authorized and writable. Inspect relevant upstream primary documentation when technical feedback depends on changing APIs/tools. Do not blindly sync upstream changes, replace permission settings, or add a mandatory process from one anecdote. For a substantive skill correction, try a realistic safe example and obtain an independent review when useful; check that the description still selects the right tasks.

Review the source diff, run relevant repository checks, and preview the native installer. Use `scripts/manage.py --only policy`, `--only roles`, or `--only skills` for a targeted preview, and the same selector with `--apply` for activation through the installer's snapshots, backups, and restore. A group includes all its managed files: inspect every previewed difference and compare against pre-edit state. Activate only if every changed target is attributable to the current correction and has no unrelated pending source/installed edits. Otherwise leave activation pending and provide the minimal proposed patch; never publish unrelated changes merely because they share a group. Install only affected managed policy/role/skill targets; do not overwrite unrelated configuration drift. If targeted activation is unavailable safely, report the pending activation rather than editing installed duplicates or claiming success. Never read a secret file to validate the rule. Separate source changes, installed activation, and new-session requirements in the handoff, with grouped commit messages and a PR draft.

This is feedback-driven maintenance when an agent receives feedback, not a background monitor. No cross-session awareness, external messages, tracker hooks, scheduled collection, or access to another agent's private sessions is implied.
